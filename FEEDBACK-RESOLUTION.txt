WHERE I DEPARTED FROM THE SUGGESTIONS
-------------------------------------

- Merge, not rebase, before rung 2. The item branch is already pushed, and
  no session rewrites pushed history.
- The config key is jira.children_command, not list_children_command.
- The board is its own branch, "board", not a file on the default branch,
  so the job never pushes to a protected default branch.
- A track lease is never deleted. The earlier spec said "delete it to
  release", which a protected branch does not allow. The lease branch is
  updated in place.


WHAT I ADDED THAT THE REVIEW DID NOT ASK FOR
--------------------------------------------

- The coordination protocol as a tool, dq, with a self-test of 254 checks
  against simulated machines. Prose would have been read several hundred
  slightly different ways.
- One spotlight lock per workspace and one worktree per item, because
  several sessions share a machine.
- Frozen proofs: a change after the freeze puts a flag on the board.
- Closed items leave the board. Quiet claims are listed on it.
- Heartbeat pushes must not start pipelines.


WHAT I ASSUMED
--------------

- llm-wiki is the format of Atlas, not a second source. You described
  Atlas as "llm wiki style". If you also run a separate wiki, set
  knowledge.llm_wiki in environment.yaml; it is then treated as context.


WHAT ONLY YOUR ENVIRONMENT CAN SETTLE
-------------------------------------

Nothing here has run against your GitLab, Jira, tracks or Claude Code
version. delivery-system/README.txt has the checklist. The parts that
decide whether it works:

- Branch protection on the queue repo. "dq protect-check" tests it.
- The board job, and archiving closed claims.
- Who posts the Jira comments.
- What triggers a track deploy and where the results come back.
- The hook and permission settings, against the Claude Code version you
  run.
